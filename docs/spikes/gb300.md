# Spike: how NVIDIA GB300 compute trays expose inventory over Redfish

Date: 2026-10-24. Time-boxed research for an `nvidia-gb300` server platform. Public sources only. Nothing here
was tested against a live BMC.

## Question

"GB300" here is the compute tray of NVIDIA's GB300 NVL72 rack: two GB300 Grace Blackwell Ultra superchip
boards per tray, each one Grace CPU and two Blackwell Ultra GPUs, so 2 CPUs and 4 GPUs per tray, 18 trays per
rack [S16, S8]. What does racklint need to know to read and judge one?

racklint reads a server today as follows (`src/racklint/redfish.py`, `read_inventory`, and
`src/racklint/checks.py`):

- serials: the `SerialNumber` of every ComputerSystem; `SerialCheck` passes if the planned serial is any of
  them;
- processors: every member of every System's `Processors`; `GPU_RULES` counts `ProcessorType` `GPU`, else
  `Accelerator` of the planned model, and compares each GPU's `Model` with the planned model;
- memory: every `Memory` member of every System whose `Status.State` is `Enabled` is a DIMM, and its
  `CapacityMiB` is read with `module["CapacityMiB"]`; `MemoryCheck` compares the count and the total exactly;
- NIC ports: each Chassis's `NetworkAdapters`, their `NetworkDeviceFunctions`, else their `Ports`; a port's
  MAC is `Ethernet.PermanentMACAddress`/`MACAddress` of a function, or the first `AssociatedMACAddresses` of a
  port;
- firmware: every `FirmwareInventory` member, matched by `Id` with `fnmatch` and compared by exact `Version`;
- login: anonymous service root (Basic on 401/403), then one Redfish session, else Basic.

The seven questions of the brief are answered in Findings 1 to 7.

Confidence levels: **high** = read in source code on the branch named, or in a captured Redfish payload;
**medium** = derived by combining several files, or a mock whose code says it mirrors a real capture; **low**
= a WebSearch snippet only (docs.nvidia.com, pubs.lenovo.com, hpe.com, opencompute.org and dmtf.org could not
be fetched from here).

No public source found holds a raw GB300 Redfish capture. The closest are a raw capture of an NVIDIA **GB200**
NVL tray [S7], and hand-written mocks of three **GB300** trays whose code says their values mirror real
scrapes [S8]. GB300 trays run the same NVIDIA firmware layers as GB200 (Finding 1), so GB200 evidence is used
where GB300 evidence is missing, and marked as such.

## Findings

### 1. Systems

- **Two managers per tray.** A GB200/GB300 compute tray has a host BMC and a second controller, the HMC, which
  manages the CPU/GPU boards [S14 low; S1 high]. The HMC runs NVIDIA's OpenBMC with Systems Id
  `HGX_Baseboard_0`, manager `HGX_BMC_0`, device prefix `HGX_` (`meta-hmc` bmcweb bbappend) [S1]. The host BMC
  runs with Systems Id `System_0` and manager `BMC_0` (`meta-bmc` bmcweb bbappend) [S1]. High.
- **Redfish aggregation.** The host BMC is built with `-Dredfish-aggregation=enabled` and prefix `HGX`, and
  entity-manager's `HMC_SAT.json` registers the HMC as a `SatelliteController` at an internal address, port
  80, `AuthType` `None` [S1]. bmcweb merges the satellite's members into its own top-level collections,
  `Systems`, `Chassis`, `Managers` and `UpdateService/FirmwareInventory` among them (`topCollections`,
  aggregation_utils.hpp line 23), and prefixes the first Id after a collection with `HGX_` unless it already
  starts with `HGX_` (`addPrefixToStringItem`, redfish_aggregator.hpp lines 223-320) [S3]. So the HMC's
  `HGX_Baseboard_0` and `HGX_FW_GPU_0` keep their names on the host BMC. racklint only talks to the host BMC.
  High (code).
- **What the tray lists.** The GB200 capture's `Systems` has exactly `System_0` and `HGX_Baseboard_0` [S7].
  All three GB300 mocks (DGX, Lenovo, Supermicro) model the same two Ids [S8]. High for GB200 (capture);
  medium for GB300 (scrape-based mocks).
- **GB300 is the same firmware family.** NVIDIA's OpenBMC has no separate GB300 machine. The GB200 NVL layers
  select GB300 by FRU product name: `HMC_C2G4_GB300.json` probes `'GB300( MaxQ)? 1CPU: ?2GPU .*'`, and the HMC
  static inventory from which the GPU processors and memory follow probes `'GB[2-3]00( MaxQ)? 1CPU: ?2GPU .*'`
  [S1]. The same files existed in May 2025 [S2]. The GB300 mocks report HMC firmware `GB200Nvl-25.08-B` "same
  on GB200/GB300" [S8]. High.
- **Which serial is the tray's.**
  - `HGX_Baseboard_0.SerialNumber` is the board serial of the FRU on HMC bus 1, address 0x50
    (`common/System.json`) [S1], the first CPU/GPU module. In the capture it equals `HGX_ProcessorModule_0`'s
    serial and its `Model` is `GB200 NVL` [S7]. It is a module serial, not the tray's. High.
  - `System_0.SerialNumber` is configured as the board serial of the FRU on bus 6, address 0x50 (the power
    distribution board), with the FRU's chassis serial in a separate `ChassisSerial` property that bmcweb does
    not publish (grep of S3) [S1]. In the GB200 capture `System_0` has **no** `SerialNumber` at all [S7]. The
    DGX GB300 mock gives `System_0` and `Chassis_0` separate serials [S8].
  - `Chassis_0` (`ChassisType` `Shelf` in the capture, `RackMount` in the DGX GB300 mock) carries a serial in
    every source, equal to `PDB_0`'s in the capture [S7, S8].
  - So the tray serial is most likely `Chassis_0.SerialNumber`, which racklint does not read. Which FRU field
    is printed on the tray label is unknown. Medium.
- **Models seen.** `System_0` model `GB300 Titania-Bianca Compute Tray` (DGX), `HG635N_V2` (Lenovo), `GB NVL`
  (Supermicro); `HGX_Baseboard_0` model `GB300 1CPU:2GPU Board PC` in all three [S8]. Medium. The HMC's model
  was hard-coded `GB200 NVL` in May 2025 and is the FRU product name since [S2, S1]. High.
- racklint on S7: `serials` holds only the module serial. A NetBox tray serial would fail `SerialCheck`.

### 2. GPUs

- **Where.** `Systems/HGX_Baseboard_0/Processors/GPU_0` to `GPU_3`; CPUs are `CPU_0` and `CPU_1` in the same
  collection [S7]. The HMC configuration creates `GPU_0`..`GPU_3` as entity-manager `Accelerator` items with
  `AcceleratorType.GPU` (`c1g2/gb200nvl_processor_systems_gpu_bianca.json`) [S1]. High.
- **`ProcessorType` is `GPU`, not `Accelerator`.** NVIDIA's bmcweb first writes `Accelerator`, as upstream
  does (processor.hpp line 646), then, in the callback that reads the item, `populatePowerState` reads
  `Item.Accelerator.Type` and overwrites `ProcessorType` with `getProcessorType`, which maps
  `AcceleratorType.GPU` to `"GPU"` (nvidia_processor.hpp lines 63-82, 4217-4235) [S3]. The same mapping is on
  every branch checked from mid-2025 to October 2026 [S4]. The capture shows `"ProcessorType": "GPU"` on all
  four [S7]. High. So racklint's `RedfishGpus` rule, not `OpenBmcAccelerators`, finds them.
- **No PCIeDevices.** No `PCIeDevices` collection in the capture has a member, under Systems or Chassis [S7].
  The GPUs also appear as Chassis `HGX_GPU_0`..`HGX_GPU_3` (`ChassisType` `Component`) [S7, S8]. High (GB200).
- **`Model`.** nsmd fills the GPU's `Model` from the NSM inventory property `MARKETING_NAME` (or
  `PRODUCT_NAME`) that the GPU reports at run time (`nsmInventoryProperty.hpp` lines 52-54, 110-113) [S5], so
  no source file holds the string. In the GB200 capture the four GPUs have **no** `Model`, `SerialNumber` or
  `PartNumber`, though `PowerState` is `On` [S7]. The GB300 mocks give Chassis `HGX_GPU_n` the model `NVIDIA
  GB300` [S8], and infra-controller's explorer recognises a GB300 tray by exactly that chassis model
  (`is_gb300`, chassis.rs line 210) [S8]. The GB200 mock uses `GB200 186GB HBM3e` for its GPUs [S8]; its
  provenance is not stated. The GB300 Processor `Model` is therefore probably `NVIDIA GB300`, unconfirmed.
  Low.
- racklint on S7: 4 GPUs found, each with model `''`. The count is right; `GpuCheck` would report each GPU's
  model as wrong, because it is missing.

### 3. Memory

- **What is listed.** The capture lists, under `HGX_Baseboard_0/Memory`: `GPU_0_DRAM_0`..`GPU_3_DRAM_0` (HBM)
  and `ProcessorModule_0_Memory_0`, `ProcessorModule_1_Memory_0` (Grace LPDDR5X); and under `System_0/Memory`:
  `Memory_0`, `Memory_1` (the same LPDDR5X, from the host's SMBIOS through `smbios-mdr`) [S7, S1]. All eight
  are `Enabled`. High (GB200).
- **Fields.** Both LPDDR5X views have `MemoryType` `DRAM`, `MemoryDeviceType` `LPDDR5_SDRAM`, `CapacityMiB`
  491520 (480 GiB per Grace on GB200) [S7]. The HBM entries are configured with D-Bus `DeviceType.HBM` and
  `Ecc.SingleBitECC` (`c1g2/gb200nvl_gpu_chassis_bianca.json`) [S1]; bmcweb maps `HBM` to `MemoryDeviceType`
  `HBM` and `MemoryType` `DRAM`, and writes `CapacityMiB` only when `MemorySizeInKB` exists (memory.hpp lines
  140-150, 498-501, 605-622) [S3]. nsmd sets `MemorySizeInKB` from the GPU's reported maximum capacity
  (`NsmMemCapacity::updateReading`, nsmMemory.cpp line 760) [S5]. High (code).
- **HBM without capacity.** In the GB200 capture all four `GPU_n_DRAM_0` are `Enabled` and have no
  `CapacityMiB`, `MemoryType` or `MemoryDeviceType` [S7]. High (one capture).
- **GB300 sizes.** Vendors list 288 GB HBM3e per GPU, one lists 279 GB, and 480 GB LPDDR5X per Grace [S16
  low]. What a GB300 reports in `CapacityMiB` is unknown.
- **The DIMM check breaks, three ways.**
  1. racklint on S7: the read fails outright with `KeyError: 'CapacityMiB'`, which `RedfishReader` turns into
     `unexpected Redfish payload` (`_dimm`, redfish.py line 255; line 76). The device gets no result for any
     check, not only memory. This also hits the default `redfish` platform on these BMCs. High.
  2. With the four HBM entries removed, racklint on S7 counts 4 DIMMs totalling 1920 GiB: each Grace's memory
     twice. `System_0.MemorySummary.TotalSystemMemoryGiB` says 960 [S7]. High.
  3. Even with no duplicates, "DIMMs" means one soldered package per CPU, plus one HBM stack-set per GPU if
     HBM counts. A NetBox `dimm_count` has no natural meaning here.

### 4. NICs

- **ConnectX-8.** On GB300 trays the IO boards carry the ConnectX-8 SuperNICs: two IO boards, two CX8 each, so
  four per tray [S1 `IO_Board_CX8.json`, S16 low]. Each CX8 is an entity-manager `NetworkAdapter` with Id
  `IO_Board_<n>_CX8_<m>`, parent chassis `IO_Board_<n>`, and an association to a PLDM state sensor port [S1].
  So it should appear at `Chassis/IO_Board_<n>/NetworkAdapters/IO_Board_<n>_CX8_<m>`. Medium (config, not
  seen).
- **What the GB200 capture shows (ConnectX-7).** `Chassis/IO_Board_<n>/NetworkAdapters/IO_Board_<n>_CX7_<m>`,
  four adapters, no `NetworkDeviceFunctions`, one `Port` in total (`IO_Board_0_CX7_0_Port_0_State`) with no
  `Ethernet` or `InfiniBand` object, and three empty `Ports` collections [S7]. High (GB200).
- **No MACs on the BMC.** nsmd can publish port MACs and GUIDs (`NsmNetworkAddressAggregator`, nsmPort.cpp
  line 2328), but only for configuration type `NSM_NVLinkWithNetworkPortAddresses` (line 3358), which no GB200
  NVL configuration uses (grep of S1) [S5, S1]. The capture has no MAC in any NIC resource and no
  `EthernetInterfaces` under `System_0` [S7]. MACs of boot-capable host NICs appear only inside UEFI device
  paths, in 12 of the capture's `System_0/BootOptions` [S7, S8]. Medium for CX8, high for the GB200 capture.
- **BlueField-3.** The host BMC lists each BlueField-3 as Chassis `Riser_Slot<n>_BlueField_3_DPU` with a
  NetworkAdapter of the same Id and an empty `Ports` collection [S7]; two on the GB200 capture, one in the
  GB300 mocks [S7, S8]. `PCIe_Cards.json` probes the card's FRU by product name `BlueField-3.*` [S1]. A
  BlueField-3 DPU also has its own on-card BMC with its own Redfish service and 1 GbE management port, where
  its FRU data is under `Chassis/Card1` [S19 low]. So yes: BlueField is a separate BMC, a second Redfish
  endpoint per tray, with its own address and credentials. Its firmware is listed on the host BMC as
  `NIC_0`/`NIC_1` [S7].
- racklint on S7: one port, no MAC. `NicCheck` would fail every planned MAC, and the port count would fail any
  plan with more than one interface.

  High (GB200 capture); the GB300 NIC Ids are medium (config).
- **NVLink.** The compute tray has no NVLink firmware item of its own. NVSwitch firmware is on the NVLink
  switch tray's BMC, as `MGX_FW_NVSwitch_0` and `MGX_FW_NVSwitch_1` [S7 `nvidia_gbswitch`]. High.
- **Stability of Ids.** The HMC `fw_uuid_mapping.json` (`HGX_FW_{FPGA,BMC,CPU,GPU}_n`) and the host BMC's
  (`FW_BMC_0`) are identical in May and November 2025 [S2, S1]. The October 2026 mocks use the same `HGX_`
  names [S8]. The Ids come from configuration files, not from the devices. High for NVIDIA's own BMC over that
  period.
- **Stability of versions.** Version strings change form across releases: the host BMC reported
  `GB200Nvl-24.12-8` in the capture [S7], `GB200Nvl-25.06-A` in the Wiwynn GB200 mock, and `HR-2511-02.0` as
  the manager firmware in the DGX GB300 scrape, whose HMC still says `GB200Nvl-25.08-B` [S8]. infra-controller
  strips the `GB200Nvl-` prefix from GB200 versions before comparing (inventories.rs lines 68-75) [S8].
  Medium.
- **Other vendors' host BMCs differ.** The Lenovo GB300 mock lists a single host firmware item `BMC`, and the
  Supermicro mock models none [S8]. The `HGX_*` items come from the NVIDIA HMC on every vendor's tray. Low for
  the Lenovo Id (the version in the mock looks synthetic).

### 6. The BMC

- **Three host BMC stacks for GB300.** infra-controller classifies GB300 trays as `DgxGb300` (NVIDIA "GB BMC",
  ServiceRoot `Vendor` `NVIDIA`, the same family as GB200), `LenovoGb300` (AMI host BMC, manager firmware
  `3.00.0` in the mock) and `SupermicroGb300` (Supermicro OpenBMC host BMC, ServiceRoot `Product` `GB NVL`,
  firmware `70.01.00.14`) (hw/mod.rs lines 43-73; the mocks' doc comments) [S8]. On all three the HMC is
  NVIDIA's [S8]. HPE's QuickSpecs name "NVIDIA OpenBMC" on an ASPEED AST2600 [S12 low]. NVIDIA's layer also
  carries a `gb300nvl-bmc-ast2700-a1` machine override, so some GB300 host BMCs are AST2700 [S1]. Medium.
- **NVIDIA's stack.** It is NVIDIA's public bmcweb fork, which keeps NVIDIA additions in `nvidia_*.hpp` files
  and upstreams some of them (`NVIDIA_DEVELOPING.md`) [S3]. Upstream OpenBMC has a minimal `gb200nvl-obmc`
  machine and no GB300 machine [S9]; shipping trays run the fork. The GB200 capture's ServiceRoot says
  `Vendor` `NVIDIA`, `Product` `GB200 NVL`, `RedfishVersion` `1.17.0` [S7]. High.
- **Login.** bmcweb's `basic-auth`, `session-auth`, `xtoken-auth` and `cookie-auth` default to enabled
  (meson.options lines 332-360) [S3], and no GB200 NVL layer turns them off [S1]. The capture's ServiceRoot
  links `Sessions` at `/redfish/v1/SessionService/Sessions`, and `AccountService` reports `HTTPBasicAuth`
  `Enabled` with `BasicAuth` and `SessionToken` true; `AccountLockoutThreshold` is 0 [S7]. So racklint's
  session login, and its Basic fallback, match NVIDIA's stack. High for the configuration; not tested. For the
  AMI and Supermicro host BMCs: unknown.
- **Defaults.** NVIDIA's DGX docs give `admin`/`admin` as the default BMC login, to be changed at first boot
  [S20 low]. How a GB300 BMC answers a read before the password is changed is unknown.
- **Read cost and stalls.** The capture's `Chassis` collection has 42 members [S7], and racklint GETs every
  Chassis member. infra-controller skips `Chassis/ERoT_BMC_0` and tests that a 30-second hang there must not
  stall exploration (`explore_dgx_gb300_skips_erot_bmc_chassis`, `..._succeeds_when_erot_bmc_hangs`) [S8],
  which suggests that resource can be slow on real trays. racklint's read timeout is 15 seconds with retries.
  Low.
- **The HMC is behind the BMC.** The aggregator forwards each request for an `HGX_` resource to the HMC and
  merges the HMC's collection members into the host BMC's on every collection read (redfish_aggregator.hpp,
  `processCollectionResponse`) [S3]. What the host BMC returns while the HMC is down or booting was not
  determined. If `HGX_Baseboard_0` is missing, racklint would see no GPUs. Medium.

### 7. The rest of the rack (for later; no design)

- **NVLink switch trays** have their own BMC, read over Redfish: ServiceRoot `Product` `P3809`, one System
  (`System_0`, model `N5110_LD`), Chassis `MGX_NVSwitch_0` and `MGX_NVSwitch_1`, a Fabric
  `MGX_NVLinkFabric_0`, and `MGX_FW_*` firmware items [S7 `nvidia_gbswitch`]. High (capture). NVIDIA documents
  a switch BMC user manual [S18 low].
- The switch tray's host runs **NVOS**, managed through its NVUE REST API; NVOS bundles the subnet manager,
  the fabric manager, NMX-Controller and NMX-Telemetry [S8 `nvos.rs`, from an October 2026 capture of an NVOS
  25.02 tray; S17 low]. One switch per NVLink domain leads; its telemetry app advertises `gnmi` among its
  capabilities [S8, S17]. NVLink partitions are managed by gRPC to NMX-Controller or the NVOS CLI [S17 low].
- **Power shelves** speak Redfish (Delta and Lite-On mockups and mocks) [S7, S8].
- **Position.** Each compute tray's `CBC_<n>` chassis carries `Oem.Nvidia` (`NvidiaCBCChassis`) with
  `ComputeTrayIndex`, `ChassisPhysicalSlotNumber`, `TopologyId` and `RevisionId` [S7]. A later rack-level
  check could compare a tray's reported index with its NetBox position. infra-controller's NVL72 simulator
  places 18 compute trays at U11-18 and U28-37 and 9 switch trays at U19-27 [S8]; that is one layout, not a
  standard.
- Rack-level management sits in NMX-Manager / NVIDIA Mission Control, above the trays [S17 low]. Not examined

## What this means for an nvidia-gb300 platform

- **racklint's default reader fails on these BMCs today.** On the GB200 capture, `read_inventory` raises on
  the HBM `Memory` resources without `CapacityMiB`, and the whole device errors. This is independent of any
  platform, and the default `redfish` platform would hit it on a GB200 or GB300 tray.
- **The platform needs its own reader, not only its own checks.** The `ServerPlatform.reader()` hook exists
  for this (`OpenBmc` overrides only `checks()`). What a reader must handle, from the findings:
  - the serial from `Chassis_0` rather than from the Systems;
  - the same Grace processors and LPDDR5X in both Systems;
  - HBM listed as `Memory`, sometimes without capacity.
- **The GPU rule already fits.** `ProcessorType` `GPU` under `HGX_Baseboard_0` is what `RedfishGpus` counts.
  The model comparison is the weak part: the model can be missing, and its GB300 value is unconfirmed.
- **The memory check needs a meaning for NetBox.** A count of soldered LPDDR5X packages plus HBM stacks is not
  a DIMM count. Whether to judge CPU memory, GPU memory or both, and by count or capacity, is a design
  question.
- **The NIC check cannot use MACs from the BMC.** No source puts CX8 or BlueField MACs in a NIC resource. Port
  counts are unreliable too (one port for four adapters in the capture). The BlueField BMC is a second
  endpoint.
- **Firmware rules can match the Ids as they are.** `HGX_FW_GPU_*`, `HGX_FW_CPU_*`, `FW_BMC_0` work with
  racklint's `fnmatch` rules. The approved versions must be written as the BMC prints them, prefix included.
- **One platform or several.** The HMC side (`HGX_*`) is NVIDIA's on every tray; the host BMC side differs by
  vendor (NVIDIA, AMI, Supermicro). A GB300 platform may need to tolerate all three, or name only NVIDIA's.
- **Feasibility.** The structure is known well enough from public code and one GB200 capture to start a
  design. The values a check compares are not: the GB300 GPU `Model`, the HBM and LPDDR5X `CapacityMiB`, the
  tray serial field, the CX8 ports, and the AMI and Supermicro host BMCs. These need real, anonymised GB300
  payloads before an implementation can be trusted. That fits a "help wanted" issue like
  [#2](https://github.com/riskand/racklint/issues/2) and [#3](https://github.com/riskand/racklint/issues/3).

## Unknowns

- A raw GB300 Redfish capture. Everything GB300-specific here comes from configuration files and scrape-based
  mocks, not a raw payload.
- The GB300 GPU Processor `Model`, and whether GPUs report a model when the host is off or the GPU has not
  answered NSM yet (the GB200 capture shows none with `PowerState` `On`).
- What GB300 reports as HBM and LPDDR5X `CapacityMiB`, and whether HBM capacity is ever missing on current
  firmware.
- Which FRU serial (chassis area or board area) is on the tray label and in a buyer's asset records, and
  whether `System_0` has a `SerialNumber` on current NVIDIA firmware.
- Whether CX8 adapters list ports, NetworkDeviceFunctions or MACs on any firmware.
- The AMI (Lenovo) and Supermicro host BMCs' Redfish layout, firmware Ids and login behaviour.
- How the host BMC answers while the HMC is down or still booting, and how slow aggregated requests are.
- Whether `Chassis/ERoT_BMC_0` really stalls on hardware.
- How a BMC behaves before its default password is changed.
- The public NVIDIA OpenBMC fork's `develop` was last updated in November 2025, while its bmcweb and nsmd are
  current to October 2026. Configuration may have moved since.
